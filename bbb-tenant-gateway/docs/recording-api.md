# Tenant Gateway recording API reference

This document describes the per-meeting recording feature of `bbb-tenant-gateway` and the API a tenant uses to find, download and delete recordings. It covers the four endpoints that existed before recordings were added (with their additive changes) and the three new recording endpoints, the recording state model, the error catalogue, download semantics, the recording-ready webhook (with a worked signature example), retention and deletion guarantees, and the operational pieces (environment variables, the purge timer, `add-tenant.sh`, nginx).

The machine-readable version of this reference is `docs/openapi.yaml` (OpenAPI 3.1).

## 1. Conventions

- Base URL: `https://<bbb host>/tenant-api/v1/tenants/{tenant}` (production: `https://meet.ooak.jp/tenant-api/v1/tenants/lunar-one`). nginx forwards `/tenant-api/` to the gateway, which serves the same paths without the `/tenant-api` prefix.
- Authentication: `Authorization: Bearer <tenant API key>` on every tenant endpoint. A missing or wrong key is `401 unauthorized`; an unknown `{tenant}` is `404 tenant_not_found`.
- Content type: request bodies are JSON (`Content-Type: application/json`, at most 32 KiB; larger bodies are answered with `413 payload_too_large` by the gateway, an unsupported charset or content encoding with `415 unsupported_media_type`, any other malformed body with `400 invalid_request`). Responses are JSON except the download endpoint, which streams `video/mp4`.
- Errors always use `{ "error": { "code": "...", "message": "...", "requestId": "..." } }`. `requestId` echoes a valid `X-Request-ID` request header (`[A-Za-z0-9._-]{1,100}`) or is generated by the gateway; it is also returned in the `X-Request-ID` response header.
- Meeting IDs: the tenant chooses `meetingId` (`^[A-Za-z0-9][A-Za-z0-9._~-]{0,127}$`). The gateway sends `<meetingIdPrefix><meetingId>` to BigBlueButton (for `lunar-one`: `lunar-one:<meetingId>`) and always returns the tenant's own `meetingId`. A meeting ID that belongs to another tenant is unreachable: it reads as a non-running meeting with no recordings.
- Record IDs: `recordId` is BigBlueButton's internal meeting ID, `sha1hex(<bbb meeting id>) + "-" + <createTime>`, matching `^[a-f0-9]{40}-[0-9]{10,16}$`. It is unguessable without the tenant prefix, the meeting ID and the exact create time.
- Timestamps are ISO 8601 UTC strings (`2026-10-02T02:10:00.000Z`) except `createTime`, which is BigBlueButton's millisecond epoch as a decimal string (`"1759400000000"`).
- All examples below use tenant `lunar-one`, meeting `luna-0f3b1b2a-7c7e-4b7a-9f21-2a3f1c6d8e90-5d2a9b1e-4f6c-4a8b-b2c3-9e8f7a6b5c4d` and record `3a1c8eb5b0f6f2c8c9d1e2f3a4b5c6d7e8f90123-1759400000000`. Secrets in examples are placeholders.

## 2. Endpoints

| Method | Path (relative to the tenant base URL) | Purpose | Status |
| --- | --- | --- | --- |
| POST | `/meetings` | Create (or re-create) a meeting; choose per meeting whether it is recorded | existing, `record` added to the response |
| POST | `/meetings/{meetingId}/join` | Build a join URL for one participant | existing, unchanged |
| GET | `/meetings/{meetingId}` | Meeting state including the recording state | existing, `record` and `recording` added |
| DELETE | `/meetings/{meetingId}` | End a running meeting; never touches recordings | existing, unchanged |
| GET | `/meetings/{meetingId}/recordings` | List the meeting's recordings | new |
| GET, HEAD | `/meetings/{meetingId}/recordings/{recordId}/download` | Stream the MP4 file | new |
| DELETE | `/meetings/{meetingId}/recordings/{recordId}` | Delete one recording (logical at once, physical within 10 minutes) | new |

Operational endpoints that are not part of the tenant API: `GET /healthz` (no auth, used by the installer) and `POST /internal/recording-ready` (loopback-only listener on `127.0.0.1:3198`, called by BigBlueButton; see section 9). `/tenant-api/internal/...` is blocked in nginx and does not exist on the public app.

### 2.1 POST /meetings

Request:

```json
{
  "meetingId": "luna-0f3b1b2a-7c7e-4b7a-9f21-2a3f1c6d8e90-5d2a9b1e-4f6c-4a8b-b2c3-9e8f7a6b5c4d",
  "name": "Weekly planning",
  "record": true
}
```

- `record` is optional and defaults to `false`.
- `record: true` with the tenant's `allowRecording=false` is rejected with `403 recording_not_allowed` before anything is created.
- `record: true` with `allowRecording=true` creates the BigBlueButton meeting with `record=true`, `autoStartRecording=<tenant.autoStartRecording>` and `allowStartStopRecording=<tenant.allowStartStopRecording>`. The production setting for `lunar-one` is `autoStartRecording=true` and `allowStartStopRecording=false` (set during rollout step 2, section 8.6): recording starts when the first participant joins and moderators cannot pause it. The gateway also registers its loopback recording-ready callback (`meta_bbb-recording-ready-url`) on the meeting.
- `record: false` creates the meeting without recording.

Response `201 Created` (new meeting) or `200 OK` (the meeting already existed):

```json
{
  "meetingId": "luna-0f3b1b2a-7c7e-4b7a-9f21-2a3f1c6d8e90-5d2a9b1e-4f6c-4a8b-b2c3-9e8f7a6b5c4d",
  "createTime": "1759400000000",
  "created": true,
  "record": true
}
```

- `created` is `false` when BigBlueButton reported the meeting as already existing (either from the gateway's concurrency pre-check or from BigBlueButton's `duplicateWarning`).
- `record` is the value actually applied: for a new meeting it equals the request; for an existing meeting it is the existing meeting's record flag, so a re-POST with a different `record` does not change anything and the response tells you what is in force.
- The gateway remembers `recordId = sha1hex(<bbb meeting id>) + "-" + createTime` for the meeting as soon as the meeting is created, so later calls can report the recording state even before BigBlueButton lists anything.

Errors: `400 invalid_request`, `403 recording_not_allowed`, `409 meeting_limit_reached` (the tenant's `maxConcurrentMeetings` is reached), `502 bbb_api_error`.

### 2.2 POST /meetings/{meetingId}/join

Unchanged. Request `{ createTime, userId, displayName, role: "MODERATOR" | "VIEWER", autoJoinAudio?, autoShareWebcam? }`, response `{ meetingId, joinUrl }`. `createTime` must be the value returned by the create call. `403 moderator_not_allowed` when the tenant may not create moderators. The join URL is for the participant's browser only; do not fetch or log it.

### 2.3 GET /meetings/{meetingId}

One `getMeetingInfo` call to BigBlueButton plus the gateway's own state.

```json
{
  "meetingId": "luna-0f3b1b2a-7c7e-4b7a-9f21-2a3f1c6d8e90-5d2a9b1e-4f6c-4a8b-b2c3-9e8f7a6b5c4d",
  "running": true,
  "record": true,
  "recording": { "state": "recording", "recordId": "3a1c8eb5b0f6f2c8c9d1e2f3a4b5c6d7e8f90123-1759400000000" }
}
```

- `running` keeps BigBlueButton's meaning: at least one participant is in the meeting. A freshly created meeting that nobody has joined yet is `running: false` even though it exists (it expires after five minutes without a participant).
- `record` is the meeting's record flag (`true`/`false`); `null` when the meeting is gone and the gateway never saw it.
- `recording.state` is one of `none`, `recording`, `processing`, `ready`, `failed` (section 3). `recording.recordId` is set as soon as the meeting exists (it is the BigBlueButton internal meeting ID), and is `null` only when nothing is known about the meeting. `recording.reason` is present when `state` is `none` or `failed` for a documented reason (`no_recording_marks`, `deleted`, `expired`, `timeout`, or the name of a BigBlueButton failure marker such as `published/<id>-video.fail`).

While the meeting exists: `state` is `recording` when `record` is true and at least one participant has joined, otherwise `none`. After the meeting has ended, the state follows the recording pipeline (section 3) for the latest session of that meeting ID. If the same `meetingId` was created several times, the newest session (by `createTime`) is reported here; the list endpoint shows all of them.

### 2.4 DELETE /meetings/{meetingId}

Unchanged. Ends the meeting; response `202 { "meetingId": "...", "status": "ending" }`. It never deletes recordings: ending a recorded meeting is exactly what starts the processing pipeline.

### 2.5 GET /meetings/{meetingId}/recordings

```json
{
  "items": [
    {
      "recordId": "3a1c8eb5b0f6f2c8c9d1e2f3a4b5c6d7e8f90123-1759400000000",
      "meetingId": "luna-0f3b1b2a-7c7e-4b7a-9f21-2a3f1c6d8e90-5d2a9b1e-4f6c-4a8b-b2c3-9e8f7a6b5c4d",
      "state": "ready",
      "startedAt": "2026-10-02T01:00:12.000Z",
      "endedAt": "2026-10-02T01:45:30.000Z",
      "durationSec": 2718,
      "mime": "video/mp4",
      "sizeBytes": 734003200,
      "filename": "luna-0f3b1b2a-7c7e-4b7a-9f21-2a3f1c6d8e90-5d2a9b1e-4f6c-4a8b-b2c3-9e8f7a6b5c4d-3a1c8eb5b0f6f2c8c9d1e2f3a4b5c6d7e8f90123-1759400000000.mp4",
      "downloadUrl": "https://meet.ooak.jp/tenant-api/v1/tenants/lunar-one/meetings/luna-0f3b1b2a-7c7e-4b7a-9f21-2a3f1c6d8e90-5d2a9b1e-4f6c-4a8b-b2c3-9e8f7a6b5c4d/recordings/3a1c8eb5b0f6f2c8c9d1e2f3a4b5c6d7e8f90123-1759400000000/download",
      "playbackUrl": null,
      "createdAt": "2026-10-02T01:46:10.000Z",
      "expiresAt": "2026-11-01T01:45:30.000Z",
      "error": null
    }
  ]
}
```

RecordingItem fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `recordId` | string | Recording identifier (BigBlueButton internal meeting ID). |
| `meetingId` | string | The tenant's meeting ID (prefix stripped). |
| `state` | `processing` \| `ready` \| `failed` | Pipeline state (section 3). Deleted and expired recordings are omitted from the list. |
| `startedAt`, `endedAt` | string \| null | Meeting start and end from BigBlueButton; `null` while unknown. |
| `durationSec` | integer \| null | Length of the MP4 in whole seconds (BigBlueButton's video `<duration>` rounded). `null` unless `ready`. |
| `mime` | `"video/mp4"` \| null | Always `video/mp4` when `ready`. |
| `sizeBytes` | integer \| null | File size; equals the `Content-Length` of the download. |
| `filename` | string \| null | `<meetingId>-<recordId>.mp4`; also sent as `Content-Disposition`. |
| `downloadUrl` | string \| null | Absolute URL of the download endpoint. Present only when `ready`; call it with the same Bearer token. |
| `playbackUrl` | null | Always `null` (section 2.9). |
| `createdAt` | string \| null | When the MP4 was published (file modification time). `null` unless `ready`. |
| `expiresAt` | string \| null | `endedAt + recordingRetentionDays`; the gateway deletes the recording after this instant. `null` while `endedAt` is unknown. |
| `error` | string \| null | Failure reason when `failed` (`no_recording_marks`, `timeout`, or a BigBlueButton marker name). |

Rules:

- Items are sorted by `startedAt` (falling back to `createTime`) ascending.
- One meeting ID produces one item per BigBlueButton session. If the same `meetingId` is created again after it ended, a second item appears with its own `recordId`.
- Only recordings whose BigBlueButton metadata carries this tenant's ID and this meeting ID are listed; other tenants' recordings are never visible.
- A session is listed only when something exists for it: BigBlueButton lists it, a status marker or file exists, or the gateway has a final outcome. A meeting that was created but produced nothing yet does not appear.
- Pause and resume inside one meeting never produce several items. BigBlueButton stitches the recorded segments into one MP4 and skips the gaps; `durationSec` is the sum of the recorded segments, which can be shorter than `endedAt - startedAt`.
- A meeting with `record: true` whose participants never produced recordable content ends without "recording marks". It appears as `state: "failed"`, `error: "no_recording_marks"` and no file. Treat it as "no recording exists" and delete it or ignore it.
- `state: "processing"` items have `null` in every media field.

### 2.6 GET /meetings/{meetingId}/recordings/{recordId}/download

Streams the recording file to the caller. Semantics (section 4): `200` full body or `206` partial body on a satisfiable `Range`, headers `Content-Type: video/mp4`, `Content-Length`, `Accept-Ranges: bytes`, `ETag`, `Content-Disposition`, `Cache-Control: no-store`. `HEAD` returns the same headers without a body.

Errors: `404 recording_not_found` (unknown, another tenant's, malformed, or already deleted `recordId`), `409 recording_not_ready` (state is `processing`, `failed` or `none`; the message names the state and reason), `416 range_not_satisfiable`, `429 too_many_downloads` or `429 rate_limited`.

### 2.7 DELETE /meetings/{meetingId}/recordings/{recordId}

Deletes one recording. Allowed only in a terminal state (`ready`, `failed`, or `none` because of `no_recording_marks`); while BigBlueButton is still processing it the call returns `409 recording_not_ready` (retry later or wait for the webhook).

Response `202 Accepted`:

```json
{ "recordId": "3a1c8eb5b0f6f2c8c9d1e2f3a4b5c6d7e8f90123-1759400000000", "status": "deleting" }
```

After the `202`, the recording is invisible immediately: the list omits it, `GET /meetings/{id}` reports `recording.state: "none"` with `reason: "deleted"`, and both download and a second `DELETE` answer `404 recording_not_found`. Physical removal from BigBlueButton storage and from the Wasabi archive happens within ten minutes (section 5). `503 recording_delete_unavailable` means the gateway could not persist the deletion request and nothing was changed; retry.

### 2.8 Rate limiting and concurrency

| Limit | Default for `lunar-one` | Exceeded |
| --- | --- | --- |
| Requests per minute per tenant (`requestsPerMinute`), downloads included | 120 | `429 rate_limited` with `Retry-After: <seconds>` |
| Concurrent meetings per tenant (`maxConcurrentMeetings`) | 20 | `409 meeting_limit_reached` on create |
| Concurrent download streams per tenant (`maxConcurrentDownloads`) | 4 | `429 too_many_downloads` with `Retry-After: 5` |
| Participants per meeting (`maxParticipantsPerMeeting`) | 100 | enforced by BigBlueButton |
| JSON request body | 32 KiB | `413 payload_too_large` from the gateway (nginx enforces the same 32 KiB with `client_max_body_size`) |

A `429` must be retried after the `Retry-After` delay; it is not a business error.

Bodies that are not oversized but cannot be read are rejected before any field validation: an unsupported charset or `Content-Encoding` is `415 unsupported_media_type`, every other malformed body (truncated, wrong framing, not a JSON object) is `400 invalid_request`, and syntactically invalid JSON is `400 invalid_json`.

### 2.9 Why `playbackUrl` is always null

BigBlueButton's HTML playback pages are public-by-URL on this installation: anyone who knows the URL can play the recording without a token. The gateway therefore never returns a playback URL. The only ways to a recording are the authenticated download endpoint and the tenant's own player. The residual exposure is a recording whose `recordId` leaks together with the host name; `recordId` contains a SHA-1 of the namespaced meeting ID and the millisecond create time, which cannot be guessed. Deleting a recording (manually or by retention) removes the playback files as well.

## 3. Recording state model

The gateway derives a single state for each recording from BigBlueButton's status markers, the presence of the published MP4, its own tombstones (section 5) and the outcome it stored when it last saw a terminal state.

| Situation | `GET /meetings/{id}` `recording.state` | List item `state` | Download | DELETE |
| --- | --- | --- | --- | --- |
| Meeting created with `record: true`, nobody joined yet | `none` | not listed | 409 `recording_not_ready` | 409 `recording_not_ready` |
| Meeting has participants and `record: true` | `recording` | not listed | 409 `recording_not_ready` | 409 |
| Meeting ended, BigBlueButton is archiving, processing or publishing | `processing` | `processing` | 409 | 409 |
| MP4 published, no video failure marker | `ready` | `ready` | 200 / 206 | 202 |
| A video failure marker exists (`archived/<id>.fail`, `sanity/<id>.fail`, `processed/<id>-video.fail`, `published/<id>-video.fail`) | `failed` (`reason` = marker) | `failed` (`error` = marker) | 409 | 202 |
| Meeting ended without recording marks (`archived/<id>.norecord`) | `none` (`reason: no_recording_marks`) | `failed` (`error: no_recording_marks`) | 409 | 202 |
| 48 hours after creation without any marker or BigBlueButton entry | `failed` (`reason: timeout`) | `failed` (`error: timeout`) | 409 | 202 |
| Deleted by the tenant or expired by retention | `none` (`reason: deleted` or `expired`) | omitted | 404 | 404 |
| Meeting created with `record: false` | `none` | `[]` | 409 `recording_not_ready` (permanent: nothing will be produced) | 409 `recording_not_ready` (permanent: nothing will be produced) |

Notes:

- `404 recording_not_found` applies only to `recordId`s the gateway never created, to another tenant's or another meeting's `recordId`, and to deleted or expired ones. A `recordId` that the gateway created but that has not (or will never) become a recording is `409 recording_not_ready`. For a meeting created with `record: false` that `409` is permanent, so do not call download or `DELETE` when `record` is `false`.
- Only the `video` format is exposed. BigBlueButton also processes a `presentation` (HTML) format independently; its markers are ignored, so a failed presentation build does not hide a successfully published MP4, and a successfully published presentation does not make a recording `ready` before the MP4 exists.
- `ready` is terminal: once a recording has been reported `ready` it never changes to `failed` (a later marker is ignored) and at most one `recording.ready` webhook is sent.
- States are evaluated on every request (no caching), so a recording that becomes ready between two calls is visible on the next call.
- Timing: BigBlueButton starts processing when the meeting ends. Measured on the production host (2026-10-02): a 2.5-minute meeting had its presentation format published 15 s after the end and its MP4 (video format) 49 s after the end, so the API reported `ready` about 50 s after the meeting ended; longer meetings take about a few percent to a bit over ten percent of their length. Plan for one to two minutes for short meetings and poll hourly plus on demand, or use the webhook.

## 4. Download semantics

- Authorization: the same Bearer token as every other call. There are no signed or unauthenticated URLs; `downloadUrl` is simply the absolute path of this endpoint.
- Methods: `GET` and `HEAD`.
- Headers on success:
  - `Content-Type: video/mp4`
  - `Content-Length: <bytes sent>` (the full size for 200, the range length for 206)
  - `Accept-Ranges: bytes`
  - `ETag: "<size>-<mtimeMs>"` (changes if the file is ever re-published)
  - `Content-Disposition: attachment; filename="<meetingId>-<recordId>.mp4"`
  - `Cache-Control: no-store`
  - `Content-Range: bytes <start>-<end>/<size>` on 206
- `Range`: a single `bytes=<start>-<end>`, `bytes=<start>-` or `bytes=-<suffix>` range is honoured with `206 Partial Content`. Multiple ranges and malformed `Range` headers are ignored and the whole file is sent with `200`. A range that starts at or beyond the file size, a `bytes=<start>-<end>` range whose `start` is greater than `end`, and the empty suffix `bytes=-0` are answered with `416 range_not_satisfiable`, a JSON error body and `Content-Range: bytes */<size>`.
- `If-Range`/`If-None-Match` are not evaluated; compare `ETag` yourself before resuming a partial download.
- The file is `video-0.m4v` as produced by BigBlueButton's video format: MP4 container, H.264 1280x720 video, AAC audio, one file per recording. Audio-only meetings still produce an MP4 (the video track shows the presentation area or a blank canvas); extract the audio with ffmpeg if required.
- The gateway reads the file from BigBlueButton's published directory and streams it; nginx buffering is disabled. nginx's `proxy_read_timeout 600s` is an inactivity timeout, not a cap on the total duration: the response is aborted only when no bytes flow for 600 s, and a slow but steady download may run for as long as it needs. Resume with `Range` after an abort.
- A gateway restart (every deploy) cuts in-flight downloads after about 10 s of graceful shutdown. Clients should treat a truncated body as retryable and resume with `Range` (compare `ETag` first).
- Concurrency: at most `maxConcurrentDownloads` (4) streams per tenant at once; a fifth request gets `429 too_many_downloads` and `Retry-After: 5`. Each download request also costs one unit of the per-minute budget.
- Logging: the access log line for a download contains the request ID, tenant, record ID, status and bytes sent. Tokens, join URLs and client bodies are never logged.

## 5. Retention and deletion

### 5.1 Retention

- Each tenant has `recordingRetentionDays` (default 30, range 1 to 3650). `expiresAt = endedAt + recordingRetentionDays`.
- An hourly sweep (`RETENTION_SWEEP_INTERVAL_MS`) lists the tenant's published and unpublished recordings in BigBlueButton, keeps only those whose meeting ID starts with the tenant prefix and whose metadata carries the tenant ID, and runs the deletion path (outcome `expired`) for every recording past `expiresAt`. Failed and timed-out sessions older than the retention period are deleted the same way so that their raw data is cleaned up too.
- Expiry is therefore not exact to the second: a recording is deleted at the first sweep after `expiresAt`, that is at most about one hour later, and physically purged at most ten minutes after that.

### 5.2 Deletion is two-phase

Phase 1, synchronous, inside `DELETE .../recordings/{recordId}` or the retention sweep, running as the unprivileged gateway user:

1. Ownership and state are checked (section 2.7).
2. A tombstone `purge/<recordId>.json` (`{ recordId, tenantId, meetingId, requestedAt }`) is written atomically into the gateway's state directory. If this write fails the call returns `503 recording_delete_unavailable` and nothing else happens.
3. The session is marked `deleted` (or `expired`) in `meetings.json`.
4. BigBlueButton's `deleteRecordings` is called, which moves the published and unpublished files into `/var/bigbluebutton/deleted/` at once. A failure or `notFound` here is logged, not surfaced; the tombstone guarantees completion.
5. `202 { status: "deleting" }`.

From this point every read path treats the tombstone as "deleted": the recording is not listed, cannot be downloaded (`404`), and cannot be deleted again (`404`).

Phase 2, asynchronous, root-only, `bbb-tenant-recording-purge.timer` every 5 minutes (`deploy/recording-purge.sh`):

1. Each tombstone is validated (`recordId` file name matches `^[a-f0-9]{40}-[0-9]{10,16}$` and equals the JSON `recordId`; otherwise it is quarantined and logged), then moved into root-owned `/var/lib/bbb-tenant-recording-purge/inflight/`.
2. The purge refuses to act (and retries next tick) if the recording is still in `published/` or `unpublished/`, which means the gateway did not logically delete it.
3. The recording must belong to a tenant configured in `/etc/bbb-tenant-gateway/tenants.json` (checked from `deleted/*/<id>/metadata.xml` or `recording/raw/<id>/events.xml`).
4. Under the Wasabi sync lock, `bbb-record --delete <id>` removes every local copy (published, unpublished, deleted, process, publish, raw, status markers, logs), then `rclone purge` removes `wasabi:<bucket>/<prefix>/<id>` from the archive (skipped when `WASABI_SYNC_ENABLED` is not `true`), then the local Wasabi markers are removed.
5. Any failure keeps the inflight tombstone for the next tick and exits non-zero, which is visible in `systemctl status bbb-tenant-recording-purge.service`.

### 5.3 Guarantees

| Event | Latest |
| --- | --- |
| Recording invisible to the API after `DELETE` returns 202 | immediately |
| Playback files moved out of BigBlueButton's published tree | immediately (synchronous `deleteRecordings`) |
| All local copies (`/var/bigbluebutton/{published,unpublished,deleted,recording/raw,...}`) removed | next purge tick, within 10 minutes |
| Wasabi archive object `wasabi:webrtc/tenants/lunar-one/recordings/<recordId>/` removed | same purge tick, within 10 minutes |
| Retention deletion after `expiresAt` | next hourly sweep, then the above |

Storage locations for `lunar-one`: local `/var/bigbluebutton/published/video/<recordId>/video-0.m4v` (and raw data under `/var/bigbluebutton/recording/raw/<recordId>` until purged) on `meet.ooak.jp`; archive copy `wasabi:webrtc/tenants/lunar-one/recordings/<recordId>/<format>/` with server-side AES-256 encryption. Both are removed by the purge.

## 6. Error catalogue

| HTTP | `error.code` | When |
| --- | --- | --- |
| 400 | `invalid_request` | Missing or malformed field, invalid `meetingId`, invalid `createTime`, unknown `role`; also any malformed request body other than oversized, unsupported encoding or invalid JSON |
| 400 | `invalid_json` | Body is not valid JSON |
| 401 | `unauthorized` | Missing or wrong Bearer token |
| 403 | `origin_not_allowed` | Browser `Origin` not in the tenant's `allowedOrigins` |
| 403 | `recording_not_allowed` | `record: true` while the tenant has `allowRecording=false` |
| 403 | `moderator_not_allowed` | `role: MODERATOR` while the tenant has `allowModerator=false` |
| 404 | `tenant_not_found` | Unknown `{tenant}` path segment |
| 404 | `not_found` | Unknown route |
| 404 | `recording_not_found` | `recordId` malformed, unknown, owned by another tenant or meeting, or already deleted/expired |
| 409 | `meeting_limit_reached` | `maxConcurrentMeetings` reached on create |
| 409 | `recording_not_ready` | Download or delete while the recording is `recording`/`processing` (download also for `failed`/`none`) |
| 413 | `payload_too_large` | JSON request body larger than 32 KiB (answered by the gateway; nginx enforces the same limit) |
| 415 | `unsupported_media_type` | Request body with an unsupported charset or `Content-Encoding` |
| 416 | `range_not_satisfiable` | `Range` start beyond the file size, `start > end`, or `bytes=-0`; `Content-Range: bytes */<size>` is set |
| 429 | `rate_limited` | Per-minute budget exceeded; `Retry-After` set |
| 429 | `too_many_downloads` | `maxConcurrentDownloads` streams already open; `Retry-After: 5` |
| 500 | `internal_error` | Unexpected gateway error |
| 502 | `bbb_api_error` | BigBlueButton rejected or failed the upstream call (message names the operation and BigBlueButton's `messageKey`) |
| 503 | `recording_delete_unavailable` | The deletion tombstone could not be written; nothing changed, retry |

Classification used by the SaaS: 400/403/409 are business errors shown to users; 401/404/413/415/416/429/5xx are integration or transient errors.

## 7. Recording-ready webhook

Optional per tenant. Configure `recordingReadyWebhook: { "url": "https://...", "secretEnv": "LUNAR_ONE_WEBHOOK_SECRET" }` in `tenants.json`; the secret (at least 16 characters) is read from that environment variable at startup and never logged.

### 7.1 Request

`POST <url>` with:

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json` |
| `X-Gateway-Timestamp` | Unix time in seconds at the moment of this delivery attempt |
| `X-Gateway-Signature` | `v1=<hex>` where `hex = HMAC-SHA256(secret, "v1:" + timestamp + ":" + rawBody)` |
| `X-Gateway-Event-Id` | `<recordId>:<event>`; identical on every retry of the same event |

Body:

```json
{
  "event": "recording.ready",
  "tenant": "lunar-one",
  "meetingId": "luna-0f3b1b2a-7c7e-4b7a-9f21-2a3f1c6d8e90-5d2a9b1e-4f6c-4a8b-b2c3-9e8f7a6b5c4d",
  "recordId": "3a1c8eb5b0f6f2c8c9d1e2f3a4b5c6d7e8f90123-1759400000000",
  "occurredAt": "2026-10-02T02:10:00Z"
}
```

- `event` is `recording.ready` or `recording.failed`. A failed event carries `"error": "<reason>"` (`no_recording_marks`, `timeout`, or a marker name) so that a consumer waiting for the recording can stop waiting.
- `meetingId` is the tenant's meeting ID (prefix stripped). The body is compact JSON without whitespace.

### 7.2 Delivery

- A delivery succeeds on any `2xx`. Redirects are not followed and count as failures. Timeout per attempt: 10 s.
- Retries after a failure: 1 min, 5 min, 15 min, 1 h, 6 h (six attempts in total, persisted in `webhooks.json` so they survive a gateway restart). After the last failure the event is dropped with a log line; the state remains available through `GET .../recordings`.
- At-least-once: the same event can arrive more than once. Deduplicate on `X-Gateway-Event-Id` (or on `recordId` + `event`).
- At most one `recording.ready` and at most one `recording.failed` per `recordId`, and never `failed` after `ready`.
- `X-Gateway-Timestamp` is recomputed on every attempt, so the signature differs between attempts. Reject timestamps older than a few minutes (five minutes is a reasonable window given the retry schedule; the retried message carries a fresh timestamp).
- The gateway detects readiness by polling BigBlueButton's status markers every 60 s (`RECORDING_POLL_INTERVAL_MS`) for every recorded meeting created in the last 48 h; BigBlueButton's own recording-ready callback to the loopback listener only makes the check immediate.

### 7.3 Verifying the signature

Verify over the raw request bytes exactly as received. Do not parse and re-serialize the JSON first.

Node.js:

```js
import { createHmac, timingSafeEqual } from 'node:crypto';

export function verifyGatewayWebhook(secret, headers, rawBody, nowSeconds = Math.floor(Date.now() / 1000)) {
  const timestamp = headers['x-gateway-timestamp'];
  const signature = headers['x-gateway-signature'] ?? '';
  if (!/^\d{1,12}$/.test(timestamp ?? '')) return false;
  if (Math.abs(nowSeconds - Number(timestamp)) > 300) return false;
  const expected = 'v1=' + createHmac('sha256', secret).update(`v1:${timestamp}:${rawBody}`).digest('hex');
  const a = Buffer.from(expected);
  const b = Buffer.from(signature);
  return a.length === b.length && timingSafeEqual(a, b);
}
```

Python:

```python
import hmac, hashlib, time

def verify_gateway_webhook(secret: str, headers: dict, raw_body: bytes, now: int | None = None) -> bool:
    timestamp = headers.get("X-Gateway-Timestamp", "")
    signature = headers.get("X-Gateway-Signature", "")
    if not timestamp.isdigit():
        return False
    if abs((now or int(time.time())) - int(timestamp)) > 300:
        return False
    message = b"v1:" + timestamp.encode() + b":" + raw_body
    expected = "v1=" + hmac.new(secret.encode(), message, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

Inputs (test values only):

### 7.5 Registering a webhook

The tenant hands the endpoint URL (HTTPS) and a secret of at least 16 characters to the gateway operator through a file on the server or another out-of-band channel, never in chat or a ticket. The operator puts the secret into `/etc/default/bbb-tenant-gateway` as the variable named by `secretEnv`, adds the `recordingReadyWebhook` block to the tenant in `tenants.json`, validates with `sudo /opt/bbb-tenant-gateway/current/deploy/check-config.sh` (section 8.4) and restarts the gateway.

### 8.4 Installing and adding tenants

- `sudo ./deploy/install.sh <release dir>` installs the release, both systemd units and the purge timer, creates `/var/lib/bbb-tenant-recording-purge/inflight` (root, 0700) and merges the environment file: installer-owned keys (`BBB_API_BASE`, `BBB_SECRET`, `BBB_CHECKSUM_ALGORITHM`, `TENANT_CONFIG_FILE`, `HOST`, `PORT`, every `<TENANT>_API_KEY_SHA256` for a `/etc/bbb-tenant-gateway/<tenant>.api-key` file) are rewritten, new keys (`INTERNAL_PORT`, `PUBLIC_BASE_URL`, `RECORDING_READY_CALLBACK_URL`) are added only if absent, every other key is kept. `tenants.json` is created only when it does not exist.
- `sudo ./deploy/add-tenant.sh <tenantId>` (`^[a-z0-9][a-z0-9-]{1,62}$`) generates `/etc/bbb-tenant-gateway/<tenantId>.api-key` (root, 0600) if absent, writes `<TENANT>_API_KEY_SHA256` into the environment file, appends a tenant block cloned from `lunar-one`'s allow-listed settings (`allowModerator`, `allowRecording`, `autoStartRecording`, `allowStartStopRecording`, `maxConcurrentMeetings`, `maxParticipantsPerMeeting`, `requestsPerMinute`, `recordingRetentionDays`, `media`, `logoutUrl`) with `meetingIdPrefix`/`userIdPrefix` set to `<tenantId>:` and empty `allowedOrigins`, backs up both files, validates the merged configuration (`dist/check-config.js` run with the merged environment, the same check as `deploy/check-config.sh`), restarts the gateway and checks `/healthz`. Webhook and meeting-ended callback settings are per environment and must be added by hand. The key is never printed: the tenant's operator reads the key file over SSH and places it in their own secret store.
- `dist/check-config.js` loads the configuration and exits 0 or 1 with a message; run it after every manual edit. It must run with the service's own environment, and `/etc/default/bbb-tenant-gateway` must never be sourced by a shell (its values use systemd `EnvironmentFile` syntax with no expansion, and sourcing would leak secrets into shell history and process listings). Use the wrapper `sudo /opt/bbb-tenant-gateway/current/deploy/check-config.sh`, or the equivalent command it runs:

  ```bash
  sudo systemd-run --quiet --wait --pipe --collect \
    -p EnvironmentFile=/etc/default/bbb-tenant-gateway \
    -p WorkingDirectory=/opt/bbb-tenant-gateway/current \
    -E STATE_DIRECTORY=/var/lib/bbb-tenant-gateway -E NODE_ENV=production \
    /usr/bin/node dist/check-config.js
  ```

### 8.6 Deploying this release (rollout checklist)

Do the steps in this order:

1. `sudo ./deploy/install.sh /opt/bbb-tenant-gateway/releases/<release>`.
2. Edit `/etc/bbb-tenant-gateway/tenants.json`: set `lunar-one.allowStartStopRecording` to `false` (`install.sh` never rewrites an existing `tenants.json`; it prints a `WARNING` when a recording tenant still allows pause/resume), optionally set `recordingRetentionDays` and `maxConcurrentDownloads`. ### 8.7 Troubleshooting

- `bbb-tenant-recording-purge.service` fails repeatedly with `still under published/ or unpublished/`: the purge refuses to touch a recording that BigBlueButton still publishes, and the gateway re-issues `deleteRecordings` for the tombstoned id every minute until BigBlueButton moves it to `deleted/`. If the message persists for more than a few minutes, bbb-web is not processing API calls; check `systemctl status bbb-web` and `journalctl -u bbb-tenant-gateway` for `bbb_api_error` lines.

### 8.5 nginx (`deploy/bbb-tenant-gateway.nginx`)

```nginx
location ~* ^/tenant-api/internal(/|$) { return 404; }
location /tenant-api/ {
  proxy_pass http://127.0.0.1:3199/;
  proxy_http_version 1.1;
  proxy_set_header Host $host;
  proxy_set_header X-Forwarded-Proto $scheme;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  client_max_body_size 32k;
  proxy_buffering off;
  proxy_request_buffering off;
  proxy_read_timeout 600s;
  proxy_max_temp_file_size 0;
}
```

Buffering is disabled so that a 700 MB download is streamed instead of spooled to disk. `proxy_read_timeout 600s` is an inactivity timeout: nginx aborts the response only when the gateway sends no bytes for 600 s; it does not cap the total duration of a download. A gateway restart (deploys) cuts in-flight downloads after about 10 s; clients resume with `Range`.

## 9. Internal recording-ready callback

`POST http://127.0.0.1:3198/internal/recording-ready` is the URL the gateway registers on every recorded meeting. BigBlueButton posts `application/x-www-form-urlencoded` with `signed_parameters=<JWT>` after each format is published (so twice per recording). The gateway verifies the JWT (`alg` must be exactly `HS256`, HMAC with `BBB_SECRET`, constant-time comparison, `exp` honoured when present), derives the tenant from the `meeting_id` prefix, records the session (so recordings of meetings created before an upgrade or after a state loss are still tracked) and triggers an immediate state check. Invalid tokens get `401`; everything else, including unknown meetings, gets `200 { "ok": true }` so BigBlueButton stops retrying. The listener is bound to loopback only, the public app never routes `/internal/*`, and nginx returns 404 for `/tenant-api/internal/...`.

### Silent recordings (audio track at -91 dB)

With `audioBridge=livekit` the conference audio never reaches FreeSWITCH; `bbb-webrtc-recorder` records every LiveKit microphone track and the recording pipeline mixes those files. The recorder needs the LiveKit API key (written by `bbb-livekit` to `/etc/default/bbb-webrtc-recorder`) and reads it only at start. A recorder process without it answers `failed to build recorder token: missing API key or secret key` (visible in `/var/log/bbb-webrtc-sfu/bbb-webrtc-sfu.log` as `LiveKitWebRTCRecorderManager: Failed to start recording`) and every recording comes out silent. Check with:

```bash
sudo tr '\0' '\n' < /proc/$(systemctl show -p MainPID --value bbb-webrtc-recorder)/environ | grep -c '^BBBRECORDER_LIVEKIT_APIKEY='
```

`0` means restart `bbb-webrtc-recorder` (the provisioning kit's `15-bbb-tune.sh` does this and `90-verify.sh` checks it). A participant who stays muted is also recorded as silence; that is expected.
